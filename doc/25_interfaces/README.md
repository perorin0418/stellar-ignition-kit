# Interfaces / Contracts

## このディレクトリの役割

このディレクトリは、本プロジェクトにおける  
**コンポーネント間・外部との接続仕様（インターフェース）を定義する拘束レイヤー**である。

ここに記載された内容は、
Feature の設計および Task の実装において
**契約（Contract）として扱う**。

---

## 上位・下位との関係

- 上位参照：
  - `05_architecture/`
  - `15_design-notes/`
- 下位拘束：
  - `20_features/`
  - `30_tasks/`

Interface は Architecture を具体化するものであり、
**新たな構成や責務を導入するものではない**。

---

## このディレクトリに置くもの

以下は **正式なインターフェース定義**としてここに配置する。

- API 定義（REST / GraphQL / gRPC 等）
- データスキーマ
- 外部サービス連携仕様
- メッセージ形式・イベント定義
- I/O フォーマット・制約条件

---

## 置いてはいけないもの

以下は **他レイヤーの責務**であり、ここには書かない。

- ビジネス要件・背景 → `00_vision.md`
- 機能仕様の説明 → `20_features/`
- 実装手順・コード例 → `30_tasks/`
- 一時的な検討メモ → `15_design-notes/`

---

## 拘束力レベル（重要）

Interface の記述は、以下の拘束力を持つ。

- **API / スキーマ定義**
  → Task は必ず準拠すること
- **フィールド名・型・必須性**
  → 勝手な追加・変更は禁止
- **未定義項目**
  → 新規追加は人の判断を要する

Task 側の都合で Interface を変更してはならない。

---

## AI / opencode 向け指示

- 実装時は本ディレクトリを **正として参照**すること
- Interface と Task の内容が矛盾する場合、
  **Task を修正対象とする**
- Interface 変更が必要な場合は、
  変更案を文章で提示し、承認を必要とする

## 記述ルール

- 曖昧な表現は禁止（「必要に応じて」「場合によって」等）
- 省略せず、明示的に定義する
- 例（Example）は補助であり、仕様そのものではない

---

## 更新ルール

- Interface の変更は **設計変更**である
- 変更理由・影響範囲を必ず記録する
- 既存定義を削除せず、後方互換性を考慮する

---

## まとめ

このディレクトリは、
**Feature が自由になりすぎないための枷**であり、
**Task が迷わず実装できるための契約書**である。

ここを守れない実装は、
正しく動いていても **不正解**と判断する。
